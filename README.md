# b24-kit-queue

Сделка в Битрикс24 → очередь в PostgreSQL → строка в кампании обзвона Voximplant Kit.

Один процесс Node.js, три части:

| Часть | Что делает | Частота |
|---|---|---|
| Приём вебхука | Проверяет `application_token` и домен, пишет заявку `new` в `b24_kit_queue` | по событию |
| Воркер Б24 | Берёт до `B24_BATCH_SIZE` заявок `new`, читает `crm.deal.get` + `crm.contact.get`, пишет результат обратно: `ready` / `skipped` / повтор | раз в 5 с |
| Воркер Kit | Берёт заявки `ready`, отправляет пачками в `campaigns/appendContacts`, успешные удаляет из очереди | раз в 60 с |
| Сверка | Подбирает сделки, чьи вебхуки не дошли (сервер был недоступен) | раз в 15 мин |

Строка, которая уходит в Kit:

```json
{"phone1":"79250802816","contact_link":"https://<portal>/crm/contact/details/<contact_id>","deal_link":"https://<portal>/crm/deal/details/<deal_id>","task_priority":"1"}
```

## Запуск

Развёртывание на сервере — в [DEPLOY.md](DEPLOY.md). На чистой Ubuntu:

```bash
git clone https://github.com/Umkladet/bitrix24-kit-pds2connector.git /opt/b24-kit-queue && sudo bash /opt/b24-kit-queue/deploy/install.sh
```

Локально нужны Node.js ≥ 20 и PostgreSQL. Таблицы создаются автоматически при старте (`schema.sql`, идемпотентно).

```bash
cp .env.example .env    # заполнить
npm ci
npm run dev             # локально, читает .env
npm start               # прод: переменные окружения задаются снаружи
```

Через Docker Compose (приложение + PostgreSQL + Caddy с HTTPS):

```bash
cp .env.example .env    # заполнить, включая APP_DOMAIN и POSTGRES_PASSWORD
docker compose up -d --build
```

Проверка живости: `GET /health` (проверяет и соединение с БД).

## Настройка Битрикс24

1. **Входящий вебхук** с правами `crm`, лучше от служебного пользователя. URL указать в `B24_REST_URL`.
2. **Исходящий вебхук**: URL `https://<хост>/b24/webhook`, события «Создание сделки» и/или «Обновление сделки». Его токен указать в `B24_APP_TOKEN`.
3. Если сделка должна уходить в обзвон на конкретной стадии, задать `B24_TRIGGER_STAGE_ID`, например `C0:NEW`. Без этого фильтра каждая сделка отправляется один раз, при первом событии.

## Переменные окружения

Полный список с дефолтами — в `.env.example`. Обязательные: `DATABASE_URL`, `B24_REST_URL`, `B24_PORTAL`, `B24_APP_TOKEN`, `KIT_DOMAIN`, `KIT_ACCESS_TOKEN`, `KIT_CAMPAIGN_ID`.

Токены хранить в секретах окружения, не в репозитории.

## Сверка

Исходящие вебхуки Битрикса не повторяются: если сервер был недоступен, сделка не попадёт в обзвон вообще. Это особенно важно на прерываемой ВМ, которая останавливается не реже раза в сутки.

Сверка запрашивает `crm.deal.list` по целевой стадии с фильтром `>DATE_MODIFY` за последние `RECONCILE_LOOKBACK_MIN` минут и добавляет в очередь сделки, которых нет ни в `b24_kit_queue` (в любом статусе), ни в `b24_kit_sent`. Дальше они идут обычным путём через воркер обогащения.

Заявки в финальном статусе (`skipped`, `b24_error`, `kit_error`) перепроверяются не чаще раза в `RECONCILE_RECHECK_MIN` минут (по умолчанию 60), пока сделка остаётся в окне сверки. Так сделка без телефона не добавляется на каждом цикле, но подхватится, если телефон контакту дописали позже.

Сверка использует тот же ограничитель частоты, что и воркер обогащения, поэтому суммарно к порталу уходит не больше `B24_RPS` запросов в секунду. Стоимость цикла — один запрос `crm.deal.list` на каждые 50 сделок в окне.

Сверка работает только при заданном `B24_TRIGGER_STAGE_ID`: без целевой стадии выборка «все сделки подряд» не имеет смысла. Если стадия не задана, при старте выводится предупреждение. Отключается через `RECONCILE_ENABLED=false`.

В логе видно, что она нашла:

```
reconcile: проверено 11, пропущенных нет
reconcile: добавлено пропущенных вебхуками сделок: 3 (2001,2004,2007)
```

Вторая строка — сигнал, что вебхуки в этот период не доходили. Если она появляется регулярно, стоит разобраться с доступностью сервера.

## Статусы очереди

| status | Значение | Дальше |
|---|---|---|
| `new` | ждёт обогащения из Б24 | воркер Б24 |
| `ready` | телефон и контакт получены | воркер Kit |
| `skipped` | финально пропущена, причина в `reason`: `no_contact`, `no_phone`, `invalid_phone`, `deal_not_found`, `contact_not_found` | удаляется через `RETENTION_DAYS` |
| `b24_error` / `kit_error` | не удалось за `MAX_ATTEMPTS` попыток, текст ошибки в `reason` | разобрать вручную |

Успешно отправленные строки удаляются из очереди и записываются в `b24_kit_sent`. Этот журнал не даёт отправить ту же сделку повторно, когда Б24 пришлёт очередной `ONCRMDEALUPDATE`.

Заявки по сделкам не на целевой стадии и по уже отправленным сделкам удаляются сразу, без сохранения: иначе поток `ONCRMDEALUPDATE` забьёт таблицу.

Полезные запросы:

```sql
-- что сейчас в очереди
SELECT status, count(*) FROM b24_kit_queue GROUP BY 1;

-- ошибки с текстом
SELECT deal_id, status, b24_status, kit_status, attempts, reason, updated_at
FROM b24_kit_queue WHERE status IN ('b24_error','kit_error') ORDER BY updated_at DESC;

-- после починки (например, перевыпустили токен) — вернуть ошибки в работу
UPDATE b24_kit_queue SET status = 'new', attempts = 0, next_attempt_at = now() WHERE status = 'b24_error';
UPDATE b24_kit_queue SET status = 'ready', attempts = 0, next_attempt_at = now() WHERE status = 'kit_error';

-- отправить сделку повторно
DELETE FROM b24_kit_sent WHERE deal_id = 123;
```

## Обработка ответов

| Ответ | Реакция |
|---|---|
| Б24 `200` | дальше по цепочке |
| Б24 `400 Not found` | `skipped` (`deal_not_found` / `contact_not_found`) |
| Б24 `401` / `403` (битый вебхук, нет прав) | повтор с backoff + `ALERT` в логе |
| Б24 `503 QUERY_LIMIT_EXCEEDED`, `5xx`, таймаут, сеть | повтор с backoff |
| Kit `200`, строка не в списках `invalid_*` | удаляется из очереди, сделка в `b24_kit_sent` |
| Kit `200`, строка в `invalid_phones` / `invalid_tz` / `invalid_personal_agent` | сразу `kit_error` с причиной `kit rejected: <список>` — повтор той же строки не поможет |
| Kit `4xx` (кроме `401`/`403`/`429`) на пачку | пачка отправляется по одной строке: валидные уходят, невалидная получает повтор с backoff и в итоге `kit_error` |
| Kit `401`/`403`, `429`, `5xx`, таймаут | повтор всей пачки с backoff; `401`/`403` → `ALERT`; остальные пачки в этом тике не отправляются |

Backoff: `min(RETRY_BASE_SEC · 2^attempt, RETRY_MAX_SEC)`, то есть 30 с, 1 мин, 2 мин … до 30 мин. После `MAX_ATTEMPTS` заявка получает статус `*_error`.

## Нагрузка

- Запросы к каждому API строго последовательные, между стартами запросов ≥ `1000/RPS` мс + 15% запаса. При `RPS=2` это ~575 мс.
- Б24: 2 запроса на лид. `B24_BATCH_SIZE=4` → ≤ 8 запросов за тик 5 с, ~48 лидов в минуту.
- Kit: 1 запрос на пачку до `KIT_CHUNK_SIZE` строк раз в минуту.
- Пик в 500 сделок разбирается примерно за 10 минут, лимит 2 RPS при этом не превышается.

**Воркеры рассчитаны на один экземпляр.** Тики выполняются под `pg_try_advisory_lock`, поэтому второй экземпляр просто пропускает тики (в логе `lock ... занят`) и лимит не нарушает. Но масштабировать горизонтально смысла нет.

## Известные ограничения

- Берётся первый валидный телефон основного контакта (`CONTACT_ID`). Нормализация под РФ: `8…` / `+7…` / 10 цифр → `7XXXXXXXXXX`. Иностранные номера получают `skipped / invalid_phone`.
- Фильтр сверки `>DATE_MODIFY` передаётся в ISO 8601 со смещением зоны контейнера (UTC). При первом запуске убедитесь, что `reconcile: проверено N` показывает ненулевое N при наличии сделок на стадии — это подтвердит, что Битрикс правильно понял смещение.
- Если процесс упадёт между успешным ответом Kit и удалением строк из БД, при следующем тике пачка уйдёт повторно. Окно — миллисекунды.
- Kit отвечает `200` + `success: true` даже когда ни один контакт не принят; реальный итог в `result.success_contacts` / `failed_contacts` и списках `invalid_*`. Сервис разбирает их по `deal_link`.
- Без таймзоны Kit не обрабатывает контакт. По умолчанию включено `tz_autodetection_enabled=true` (`KIT_TZ_AUTODETECT`); альтернатива — фиксированная `KIT_TIMEZONE`.
